# Evidence guide: where evidence lives in a PR package

An eval bundle always has the same parts, in this order: `## Repo facts` (the repo's stated PR template asks and its contribution and AI-use policy, on the `- pull requests:` and `- contribution policy` lines), `## Issue`, `## Thread highlights` (each commenter's association in parentheses), `## Plan context` (the repro evidence the plan built on, then the plan itself, as a run-on paragraph beginning `Plan:` with its scope, `Not in scope`, `Files`, and `Test plan` sentences), and `## Candidate PR` with the sub-headings `### Title`, `### Description`, `### Commits`, `### Diff`, and `### Test evidence`. A bundle's plan has no separate deviation section; a deviation shows up as a sentence in the plan context or in the description that says it was recorded in the plan.

In live mode the same parts live in these places:

- Repo facts: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md` in the working copy (its branch naming, commit convention, "Working on a seeded bug" and "CI must be green" sections), plus any AI policy text it carries.
- Issue and thread: `gh issue view <number> --repo <owner/repo> --comments`; the `author_association` of each comment gives the role.
- Plan: `plan.md` in the top folder of the clone, including `## Deviations`.
- Diff and commits: `git diff main...HEAD` and `git log main..HEAD --oneline`, run on the student's branch. Only committed changes appear.
- Title and description: `pr_draft.md`; the PR title is its first line, and the rest is the filled-in template.
- Test evidence: `test_evidence.md`, and the Testing section of `pr_draft.md`.
- Not part of the package: `comment.md`, scratch repro scripts, anything else in the working directory.

## Plan fidelity (harness category: silent-drift)

- Where it lives: In a bundle, the plan context's `Plan:` paragraph gives the scope ("one bounded change"), the `Not in scope` list, the `Files` line, and the named deliverables (read for words like "two named deliverables" or an "and"); the `### Diff` and `### Commits` give what changed; the `### Description` gives the claims to check against the diff. In live mode, `plan.md` sections `## Scope`, `## Files I will touch`, `## Approach`, and `## Deviations`, read against `git diff main...HEAD --stat` and the full diff, and `pr_draft.md`'s Summary, Changes, and Notes for Reviewers.
- What good looks like: Every changed file and hunk is something the plan names, a test for the fix, follow-through the repo requires, or a deviation the plan records with a reason; every deliverable the plan names is in the diff or openly deferred; and every claim in the description is true of the diff. Silent drift runs in both directions. More than the plan: a rename pass, a new option or flag, a rewritten function the plan never names, or reworded unrelated text, sitting under a description that says "exactly as planned" or "no other changes". Less than the plan: a named deliverable (docs, a second fix) missing while the description says it is done. An honest deviation re-ties a mismatch only when it is written down (live: in `plan.md`'s Deviations; in a bundle: as a sentence in the plan context or in the description saying it was recorded) and says why the fix needed it; a deferral the plan stated up front is not drift. A claim that the description makes about the diff is graded here, not as a communication problem.

## Test evidence (harness category: not-tested)

- Where it lives: In a bundle, `### Test evidence`, read against the plan context's `Test plan:` sentence and the repro evidence's failing step and expected result, and against the tests the `### Diff` adds. The repo's own checks are named on the repo-facts `- pull requests:` and `- contribution policy` lines and in the plan's test plan (`cargo test`, `yarn test`, `go test`, `pnpm test`). In live mode, `test_evidence.md` and the Testing section of `pr_draft.md`, read against `plan.md`'s `## Test plan` and the repro in `repro54.py` or the repro comment, and against the commands `PULL_REQUEST_TEMPLATE.md` lists (`make test-unit`, `make test-integration`, `make lint`, `make typecheck`).
- What good looks like: Decisive evidence runs the repro's failing step itself (the same command, input, or action the plan's test plan names), shows what it printed before the fix and after, and states the after result the plan promised, so unfixed code would have printed something different. The repo's own checks appear with the command and the outcome (a count or a pass line). Not decisive: "tested locally", "works now", "tests pass" with no command or target; evidence that runs only the passing control, or a different input shape or method than the one that failed; a regression test whose assertions pass on the unfixed code; a failing step the test plan names that the evidence never runs. A check that failed, reported with the reason, is evidence; a check hidden is not. A check the repo cannot run yet (live: `make test-integration` printing "no tests ran") counts as run when its output is pasted as printed.

## Diff quality (harness category: unreviewable)

- Where it lives: In a bundle, `### Diff` and `### Commits`. In live mode, `git diff main...HEAD` and `git log main..HEAD --oneline`, plus `git diff main...HEAD --stat` for the file list.
- What good looks like: The fix and its test are visible and nothing else rides along: each added or removed line is part of the fix, a test for it, or a comment that explains it. Debris tells to look for in added lines: print, eprintln, console.log, or dbg calls; lines commented out; a function nothing calls, or a `dead_code` allowance; an unused import; TODO, FIXME, or WIP; a hunk that only re-indents, reorders imports, or reformats; the same lines printed twice. Commit messages such as "wip", "fmt + cleanup", or "misc cleanups while debugging" corroborate debris but never decide it. In live mode the stat should list only the files the plan names.

## Standards and comms (harness category: standards-wall)

- Where it lives: In a bundle, the repo-facts `- pull requests:` line (template sections, issue-reference line, checklist items, changelog or whatsnew entry) and `- contribution policy` line (AI-use sentences and which surface they cover), read against `### Description` and the `### Diff`'s file list; maintainer directions live in `## Thread highlights` on lines from OWNER, MEMBER, or COLLABORATOR. In live mode, `PULL_REQUEST_TEMPLATE.md` (Summary, Issue, Changes, Testing, Screenshots / Demo, Notes for Reviewers), `docs/CONTRIBUTING.md`, the course rule that the description says how AI helped, and the live thread, read against `pr_draft.md`.
- What good looks like: Every template section holds real content and not the placeholder or the HTML comment; the issue is referenced the way the template asks (`Closes #N`); checklist boxes are ticked only where true, with the CI box left alone until CI has run; an artifact the repo names (a changelog or whatsnew entry, a test, a docs change) is present in the diff, not just mentioned; and where the policy requires AI disclosure the description names the tool and the extent in the contributor's own words. In live mode that disclosure is required whatever the repo's policy says. A specific maintainer direction (a ruling, a rejected approach, a requested check, a restated rule) is followed or answered with a reason. Boilerplate that could sit on any PR, a bare checklist, or a missing disclosure is a visibly ignored ask. Whether the description's claims match the diff is plan fidelity, above.
