# Rubric: is this pull request ready to submit?

A pull request is ready when a maintainer could read it and find that it does what the posted plan said, proves it with something observable, shows only the change, and does what the repo asks of every PR. Every check reads the thing itself (the diff, the evidence, the claims), never the write-up's length, headings, or confidence. An honestly disclosed shortfall can be ready: a PR that delivers less than the plan and says so is not drifting; a PR that quietly delivers more or less, or claims more than it delivers, is.

The checks sit under the four failure families the eval names: silent drift (the first two checks), not tested (the next two), unreviewable (the fifth), standards wall (the last three).

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | The diff's changed files and hunks, read against the plan's scope, files, and approach, plus any deviation notes (the plan's `## Deviations`, or in a bundle any deviation the plan context records) | Both hold. (a) Every changed file and hunk is named or described by the plan's scope, files, or approach; or is a test for the fix; or is follow-through the repo's own template or contribution guide requires for this kind of change (for example a changelog entry); or is explained by a deviation note that says why the fix needed it. (b) Every deliverable the plan names as part of this change appears in the diff, or the plan, a deviation note, or the description says plainly that it was deferred or dropped. Fail if either (a) or (b) breaks. Typical (a) breaks: a rewrite or rename pass over code the fix does not need; a new option, flag, setting, or config key; a dependency bump; reworded unrelated text; a hunk in a file or function the plan never names. A description that mentions an unplanned extra does not make it planned; only a plan deviation note that shows the fix needed it does. Typical (b) break: the plan promises a code change and a docs update and the diff has only the code change, with nothing saying so. Not a fail: the same fix applied at sibling sites the plan or issue names; a comment that explains the fix; a deferral the plan states up front | required |
| description-matches-diff | The description's concrete claims (what changed, "implements the plan exactly" or "in full", "no changes outside X", "docs updated", "tests added", "fixes #N") read against the diff and the commit list | Every concrete claim about what the PR contains is visible in the diff or the commit list, and no claim of fidelity (such as "exactly as planned", "no other changes", "nothing beyond the plan") is contradicted by a hunk. Fail if the description says a docs update, test, flag, or behavior is in the PR and the diff does not contain it, or if a fidelity claim sits over a hunk the plan does not cover. A description that states a shortfall or deferral and the diff matches that statement passes | required |
| repro-before-after | The test-evidence section (live: `test_evidence.md` and the description's Testing section), read against the plan's test plan and the repro's failing step | The evidence re-runs the failing step the plan's test plan names (the actual command, input, or action, in the repro's own terms) and shows an observable result before the change and after it, and the after result matches the expected-after the plan names. If the test plan names more than one failing behavior, each one is re-run or the description says one was not. Any regression test the PR adds must exercise the reproduced failing behavior. Fail if any holds: (a) the evidence is a verdict with no observation ("tested locally", "works now", "colors work"); (b) it exercises a different path than the failing one (only the passing control, a different method, input shape, or platform than the repro); (c) only the before or only the after is shown, or no expected-after result is named; (d) the added test would pass on the unfixed code because it covers something other than the fix. A control only has to be stated, not transcribed | required |
| repo-checks-ran | The test-evidence section read against the commands the plan, the PR template, and the contribution guide name for the area changed (test suite, linter, type checker, build) | At least the test command that covers the changed area (and each other check the template or guide requires) is shown with its command or target and its outcome (a pass line, a count, or a named result). A check that ran red passes only if the description says the failure is outside the diff and why. Fail if any holds: (a) "tests pass" or "CI is green" with no command or target named; (b) a required check is named but its outcome is absent; (c) the only verification is "verified on my machine" with no check run; (d) a red result in the changed area is not explained. A required check the repo cannot run yet is recorded as it printed, which counts as run | required |
| diff-reviewable | The unified diff's added and removed lines, and the commit list as corroboration | Every added or removed line is part of the fix, a test for it, or a comment that explains the fix. Fail if the diff contains any of: debug output left in (print, eprintln, console.log, dbg); commented-out code; dead code (an unreferenced function or variable, a lint allowance to hide one, an unused import); a TODO, FIXME, or WIP marker; a formatting-only, whitespace, or re-indent hunk; an import reorder or restructure the fix does not need; lines repeated or re-printed with no change. Commit messages such as "wip", "misc cleanups", or "fmt" corroborate debris but never decide: grade the diff | required |
| template-asks-honored | The repo-facts block's pull-request line (live: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`), read against the description and the diff | Each concrete ask the template or guide makes of every PR that applies to this change is visibly met: each template section present with real content (not left as the placeholder or comment), the issue referenced where the template asks for it (`Closes #N`, `fixes #N`), checklist boxes ticked only where true and addressed otherwise, and any artifact the ask names (a changelog or whatsnew entry, a test, a docs change) present in the diff. Fail if an ask that applies is visibly ignored: a section empty or missing, no issue reference where one is required, a checklist untouched, a required changelog entry absent from the diff. An ask that does not apply to this change (a UI screenshot for a non-UI fix) is not a fail when the description says N/A or the change plainly has no such surface. Where the repo has no PR template, hold the PR to the asks the contribution guide states (tests with behavior changes, an issue reference, a changelog entry) | required |
| ai-disclosure | The contribution and AI-use policy line in the repo-facts block, read against the description (live: also the course rule below) | Treat every PR as AI-assisted. If the repo's policy requires AI use to be disclosed (for all contributions, or in pull requests), the description names the tool and the extent of its help; fail if it does not. If the policy only welcomes AI, asks for a human who understands the work, asks that comments be in the contributor's own words, limits its asks to issue comments, or is silent, no disclosure language is needed and the check passes. In live mode only, the course adds its own rule: the description must say in the contributor's own words how AI helped, under Notes for Reviewers, whatever the repo's policy says; fail if it is missing | required |
| thread-direction-honored | The thread highlights (live: the issue thread from `gh issue view`), read against the description and the diff | Every specific direction, ruling, rejected approach, or request from a maintainer (association OWNER, MEMBER, or COLLABORATOR, or whoever the thread shows deciding the fix), and every restated repo rule that bears on the change, is followed by the PR or answered in the description. Fail if the diff or description contradicts such a direction without saying why, or if a maintainer asked for something specific (a test, a patched-build check, a different approach) and the PR neither does it nor mentions it. Speculation from non-maintainers does not bind the PR. A thread with no comments, or with no direction that bears on the change, passes | required |
| issue-and-limits-named | The description's issue reference and any limit, deferral, or unknown the plan states, read against the description | The description names its issue by number or link, and states each limit, deferral, or unverified area the plan records, or says it found none. A PR with no stated limit is recorded here but never held for it | preferred |

## Verdict rule

Accept if every `required` check is `pass`. Reject if any `required` check is `fail`. An `unclear` grade on a required check counts as `fail`: a PR whose readiness cannot be verified from the package is not ready to submit. The `preferred` check is recorded in the output and never changes the verdict. The checks are not weighed, averaged, or counted against each other: one failed required check holds the PR, and no number of passes buys it back. A shortfall the PR discloses honestly (a deferral the plan states, a deviation the plan records, a limit the description names) is not a fail on `diff-within-plan`, `description-matches-diff`, or `repro-before-after`; an extra change or a claim the diff contradicts is.
