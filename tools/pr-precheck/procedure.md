# Procedure: how this tool grades a PR package

This procedure grades a pull request. It does not write or improve one. Follow the steps in order. Keep the notes the steps ask for: the checks are graded from those notes, not from a fresh read. Most checks put two things side by side, so every note names which side it came from.

## Read order

Read in this order, and write the note each step names before moving on. The plan is read before the diff and the description on purpose: if you read the description first, its promises anchor you and you read the diff to fit them. The diff is read before the description's claims are tested, so the claims are measured against what changed, not against what was said.

1. Read the repo facts (bundle: the repo-facts block; live: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`). Copy out, verbatim, the template's asks (each section, the issue-reference line, each checklist item, any changelog, whatsnew, test, or docs artifact it names) as the "template asks". Copy out, verbatim, each sentence of the contribution or AI-use policy that mentions AI or disclosure, and note which surface it applies to (pull requests, all contributions, issue comments, code). Write "policy: silent" if there is none. In live mode, add the course rule: the description must say how AI helped.
2. Read the issue and the thread (bundle: the issue and thread highlights; live: `gh issue view`). Write one line for the symptom, with the exact command or input. For each commenter with association OWNER, MEMBER, or COLLABORATOR, and anyone the thread treats as deciding the fix, copy each direction, ruling, rejected approach, request, or restated repo rule, verbatim, as a "maintainer direction". If the thread is empty, write "thread: empty".
3. Read the plan (bundle: the plan context; live: `plan.md`). Copy out: (a) the scope sentence and the numbered change list, as the "plan scope"; (b) every file or area named, as "plan files"; (c) every deliverable the plan names (a code change, a test, a docs update), as "plan deliverables"; (d) every deferral and "not in scope" item, as "plan deferrals"; (e) the test plan, verbatim, and the repro's failing step with its expected-after result, as "plan test"; (f) every deviation note (live: the `## Deviations` section), as "deviations". If a part is missing, write "absent: <part>".
4. Read the diff and the commit list (bundle: the Diff and Commits sections; live: the output of `git diff main...HEAD` and `git log main..HEAD --oneline`). List every changed file. For each file list its hunks in one line each: what the hunk does, in your words. Mark each hunk as fix, test, comment-only, formatting-or-whitespace, import change, or other. Note any added line that prints, is commented out, is dead, or says TODO, FIXME, or WIP. This list is the "hunk list".
5. Read the description (bundle: the Description section and the Title; live: `pr_draft.md`). Copy out every concrete claim about what the PR contains or does (changes, tests, docs, "exactly as planned", "no other changes", "fixes #N") as the "claim list", and note whether the issue is named. Copy out any AI statement verbatim, as the "AI statement", or write "no AI statement".
6. Read the test evidence (bundle: the Test evidence section; live: `test_evidence.md` and the description's Testing section). List each command or action shown, with the output or result it shows, as the "evidence list". Mark which entries are the repro's failing step, which are controls, and which are the repo's own checks.

## Evidence gathering

Each check has one gathering move, done from the notes above. In eval mode the package text is the whole world: fetch nothing. In live mode take the same facts from the places named in `references/evidence-guide.md`.

1. diff-within-plan: take the hunk list and set it beside the plan scope, plan files, and deviations. For each hunk write "covered by: <plan scope item, plan file, test for the fix, repo-required follow-through, deviation, or none>". Then take the plan deliverables and write for each "in the diff: <file or hunk>" or "missing; disclosed: <the plan, deviation, or description sentence>" or "missing; not disclosed". A hunk marked "none" is an extra.
2. description-matches-diff: take the claim list. For each claim write "found in the diff at: <file or hunk, or the commit>" or "not in the diff". For each fidelity claim ("exactly", "in full", "no other changes") write whether any hunk marked "none" in the previous gather contradicts it.
3. repro-before-after: take the plan test and the evidence list. Write: the failing step the plan test re-runs; the entry in the evidence list that runs it; the before result and the after result it shows; the expected-after the plan names; whether the after matches. If the plan test names more than one failing behavior, repeat for each. For each test the diff adds, write whether it would fail on the unfixed code, from what its assertions exercise. Write "no observable result" where an entry is only a verdict.
4. repo-checks-ran: take the template asks, the contribution guide's test and check commands, and the plan test. List the commands the repo expects for the changed area (test suite, linter, type checker, build). For each write "shown: <command, outcome>" or "not shown". For any red outcome write whether the description explains it.
5. diff-reviewable: take the hunk list. Write every hunk marked formatting-or-whitespace, import change, or other that the fix does not need, and every debug, commented-out, dead, or TODO line noted in the read order. Write "none" if there are none. Note commit messages that admit cleanup, as corroboration only.
6. template-asks-honored: take the template asks and the description. For each ask write "met: <where in the description or diff>", "not applicable: <why>", or "ignored". For a changelog, whatsnew, test, or docs ask, look in the diff's file list, not the description. For a section, check that it holds real content and not the placeholder.
7. ai-disclosure: take the policy sentences and the AI statement. Decide first whether the policy requires disclosure on a surface that includes a pull request description (see the rubric). Then write whether the AI statement names a tool and an extent. In live mode, also write whether the description says in the contributor's own words how AI helped.
8. thread-direction-honored: take the maintainer directions. For each write "followed: <diff or description quote>", "answered: <quote>", or "not addressed". Treat silence as not addressed, but only count it as a failure when the direction bears on this change.
9. issue-and-limits-named: take the description and the plan deferrals and unknowns. Write whether the issue is named, and for each deferral or unknown whether the description states it.

## Check execution

1. Execute the checks in the rubric's table order, one at a time, each graded from its gathered notes. Do not re-read the whole package for a check unless a note is missing or two notes conflict; then re-read only the part named.
2. For each check, name the deciding fact: a quote, a file and hunk, or a numbered note. A grade with no named fact is not allowed.
3. Apply the rubric's pass condition as written. A check passes only when none of its fail conditions holds. A check fails when any one holds, even if the PR is otherwise strong, polished, or confident.
4. Grade the thing, not the write-up. Do not pass a diff because the description calls it clean. Do not fail a PR for being terse. Do not count sections, commits, or lines of prose. A one-line fix with a decisive before and after, a named test run, and a filled-in template passes every check.
5. Apply the rubric's "not a fail" sentences when they cover what you found: sibling sites the plan names, comments that explain the fix, follow-through the repo requires, a deferral the plan states, a shortfall the description states.
6. Use `unclear` only when the part a check reads is missing from the package and the rubric gives no pass for its absence (for example the PR has no test-evidence section at all). An absent AI policy, an empty thread, and a repo with no template are not unclear: the rubric says how those pass. Do not use `unclear` to avoid a decision when the evidence is present.
7. Do not let one check's result decide another's. A single defect can fail two checks: a hunk the plan lacks fails `diff-within-plan`, and the description's claim that nothing else changed fails `description-matches-diff`. Grade each on its own condition.
8. If you find a gap in this procedure (a case it does not cover), say so in one line in the summary before the JSON block. Do not invent a step silently.

## Verdict assembly

1. Collect the graded checks in the rubric's order. List the required checks that are `fail` or `unclear`.
2. Apply the rubric's verdict rule exactly: `accept` only if every required check is `pass`; otherwise `reject`. Treat each `unclear` on a required check as `fail`. Do not weigh, count, or average. The preferred check never changes the verdict.
3. When more than one required check failed, the deciding check is the first failing required check in the rubric's order. Name it, and quote its deciding line, in the verdict line of the summary.
4. Before the JSON block, write one short summary line per check ("check: grade, deciding fact"), then one line naming the verdict and, if reject, every failed required check with the first one marked as the deciding check. In live mode add the voice-guide notes, the branch-name note, and any procedure gaps.
5. For every failed or unclear check, the JSON `evidence` field quotes the deciding line from the package (or the file and hunk) and says in a few words why it decides. For passing checks, it names the one fact that decided it.
6. Emit the fenced JSON block last, with the item id, every check in the rubric (the preferred one included), and a `verdict` of `accept` or `reject`. Nothing follows it.
