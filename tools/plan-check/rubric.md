# Rubric: is this plan ready to post and build from?

A plan is ready when a maintainer could read the comment and say "yes, do that", and a stranger could then build it. Every check below reads the thing itself (the cause, the changes, the test), never the write-up's length, headings, or confidence.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-fits-evidence | The plan's stated cause (its diagnosis or cause sentence), read against every numbered step, control run, and artifact in the repro-evidence block | The stated cause explains why the failing step fails AND is compatible with every control and artifact in the repro evidence. Fail if any one of these holds: (a) a control or artifact shows the component the cause blames working correctly (the control that exercises it passes, or the same component produces correct output elsewhere in the same build); (b) the repro evidence shows the failure already present at a point before the blamed component runs (the error is raised earlier, or the data is already wrong before the blamed step); (c) the cause cannot account for the difference between the failing run and a passing control (for example the failing and passing runs differ by version or flag and the blamed code does not depend on it); (d) the plan states no cause, only an intention to find one. A cause taken from the issue or the thread passes when the repro evidence bears it out and fails when it does not. A plausible mechanism that the repro evidence does not directly show passes, as long as nothing in the evidence contradicts it | required |
| change-targets-cause | The plan's list of changes and approach, read against the plan's stated cause and the repro evidence's failing step | The change acts on the place the cause names, so the repro's failing step would stop failing. Fail if the change only routes around the failure: documentation of a workaround, a catch/recover/ignore that hides the error, a warning message, or a change at a different layer than the cause the plan itself states. Fail if, after the change, the repro's failing step as written would still fail. A fix scoped to the repro's platform or variant, with the other variant stated as deferred, passes | required |
| scope-bounded | The plan's list of changes, its in-scope and not-in-scope statements, and its files, read against the failure the issue reports and the repro evidence demonstrates | Every change item is needed to stop a failure the repro evidence demonstrates, or is a test for that fix. Fail if any change item would leave the reproduced failure fixed when removed and is one of: a refactor, restructure, or new abstraction; a library, dependency, or runtime upgrade or migration; a new option, setting, prop, or UI; unrelated error handling, retries, or logging; a test-harness or CI migration or addition; or "while in the area" or "fix the whole class" work. This holds even when the core fix inside the plan is correct. Not extra: the same fix applied to sibling sites of the same defect that the issue or repro names; regression tests; an audit or verification step that changes nothing; items the plan explicitly defers or puts out of scope; follow-through the repo's own contribution guide requires for this kind of fix | required |
| executable-from-plan | The plan's files or areas, its approach, and its order of work | A stranger could open a named file, module, or code path and make a specific described change there without asking the author what to do. Fail if either holds: (a) no file, module, or code area is named for the change; (b) the change itself is left to be decided at build time, in words such as investigate, explore, look into, figure out, somewhere, whichever is easier, maybe also, or experiment with, so that the plan is a search rather than a change. Naming the module or code path without the exact function passes when the chosen change is stated. Open questions about details of a chosen change, and exact locations to be pinned during implementation, do not fail this check | required |
| test-plan-decisive | The plan's test plan, read against the repro evidence's failing step and its expected result | The test plan re-runs the repro's failing step (the command, input, or action) and names the observable result expected after the fix (specific output, exit code, or state) that unfixed code would not produce. Fail if any holds: (a) the outcome is subjective or unobservable (should feel fast, works correctly, nothing else should break); (b) the only verification is running an existing suite or CI with no result named for the fix itself; (c) what is verified is something other than the reproduced failing behavior (a documented workaround, a docs build). A named test suite passing is fine as an addition to a named repro result | required |
| thread-direction-respected | The thread highlights in the issue context, read against the plan comment and the plan | Every explicit direction, ruling, rejected approach, request, or pointer from a commenter with authority over the fix (association OWNER, MEMBER, or COLLABORATOR, or whoever the thread shows deciding the fix, such as the issue's maintainer author) is followed, or the comment says why it departs. Every open pull request or prior fix the thread names is acknowledged (built on, deferred to, or answered). Fail if the comment or plan ignores such a direction, contradicts it without a stated reason, or proposes a different change where the maintainer had already isolated the cause or asked for something specific (for example asked for a patched build to be tested). Non-maintainer speculation does not bind the plan. A thread with no comments, or with no maintainer direction and no named PR, passes | required |
| ai-disclosure-compliant | The contribution and AI-use policy line in the repo-facts block, read against the text of the plan comment | Treat every plan as AI-assisted. If the policy requires AI use to be disclosed (tool and extent) in comments, or for all contributions with no carve-out for issue comments, the plan comment itself must say which tool and how much it helped; fail if it does not. If the policy only welcomes AI, asks for human understanding or responsibility, bans fully generated work, limits disclosure to the pull request or the code with no ask for issue comments, asks only that comments be in the contributor's own words, or is silent, this check passes with no disclosure language needed | required |
| unknowns-stated | The plan's risk and open-question statements (a risk line, a stated unknown, a deferred variant), read against what the repro evidence does not establish | The plan names what it has not verified or what could go wrong with its change, or says it found none after naming where it looked. Not required for readiness: a plan with no stated unknown is recorded here but never held for it | preferred |

## Verdict rule

Accept if every `required` check passes. Reject if any `required` check is `fail`. An `unclear` grade on a required check counts as `fail`: a plan whose soundness cannot be verified from the package is not ready to build from. The `preferred` check is recorded in the output and never changes the verdict. The checks are not weighed or counted against each other: one failed required check holds the plan, and no number of passes buys it back.
